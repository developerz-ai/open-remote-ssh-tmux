Run against a built RC (`open-remote-ssh-tmux-1.0.0.vsix`, commit at branch tip
before this task) using a real, empirical rig — not simulated/mocked:

- **Client**: real VSCodium desktop (1.126.04524) run headless under a
  dedicated `Xvfb :99`, driven via `xdotool` (click/type/keys) with visual
  verification via `scrot` screenshots read back. Two isolated client
  identities (`home1` = "PC", `home2` = "laptop": separate `--user-data-dir` /
  `--extensions-dir` / `HOME`, own `~/.ssh` + known_hosts) so multi-client rows
  are genuine separate clients, not one window twice. Care was taken never to
  touch the live orchestrating session's own VS Code/tmux connection.
- **Remotes**: two Docker containers (`matrix-tmux`: Ubuntu 24.04 + tmux 3.4 +
  sshd; `matrix-notmux`: same, no tmux), reachable over real SSH
  (`ssh -p 2201/2202`), with an SSH-config alias (`matrix-tmux`,
  `matrix-notmux`) pointed at them from the client's isolated `HOME`. Windows
  was simulated via `remote.SSH.remotePlatform` forced to `"windows"` against
  the Linux container (no real Windows box available in this environment —
  disclosed as a limitation below, not silently claimed).
- Every row's remote-side assertion (`tmux ls`, `tmux list-clients`, file
  contents) was read directly over a second, independent `ssh` connection —
  not taken on the client's word.

## Bugs found and fixed during this run

Both were **wiring gaps that only a real F5/EDH run could catch** — the pure
logic they call was already unit-tested and correct in isolation; nothing was
ever calling it for real. Fixed in the owning slice (`04-terminal-profile.md`
/ `05-package-contributes.md`), covered by new regression tests, re-verified
live, then rows 1 and 6-9 (zombie rows, per the verify doc's "re-run always"
rule) were re-run to confirm.

1. **Terminal profile never actually registered (`package.json`).**
   `contributes` had a stray top-level `"terminal.profiles"` key shaped like a
   *settings* schema (copy-paste artifact) instead of the real VS Code
   extension point, which is `contributes.terminal.profiles` (an array under a
   `"terminal"` object). VS Code silently ignores unrecognized contribution
   points, so `vscode.window.registerTerminalProfileProvider('tmux', ...)` had
   no matching contribution and was a no-op: a fresh "New Terminal" launched a
   plain shell, zero tmux sessions on the remote — the entire feature was
   unreachable. Also added: making the tmux profile the actual default
   (`terminal.integrated.defaultProfile.linux`, Workspace-scoped, only when
   unset) since a contributed profile has no manifest-level "default" flag.
   Fix: `package.json` (`contributes.terminal.profiles`), `extension.ts`
   (`setDefaultTerminalProfileIfUnset`). Tests:
   `test/package-manifest.test.ts` (drift guard: contribution shape + id
   matches the `registerTerminalProfileProvider` call in `src/`).

2. **Closing a terminal never freed its slot (`extension.ts`).**
   `TmuxTerminalProvider.releaseSlot()` is pure, correct, and unit-tested in
   isolation — but nothing in `extension.ts` ever called it from a real
   `vscode.window.onDidCloseTerminal` event. Live effect: open/close a
   terminal 5 times in one window session → **5 distinct, ever-growing tmux
   sessions** on the remote instead of 1 reused slot (`tmux ls` count only
   ever went up, violating row 7's pass criterion and the "no zombies"
   invariant). Fix: `TmuxTerminalProvider.handleTerminalOpened` /
   `handleTerminalClosed` (correlate a live `vscode.Terminal` to its slot via
   the session name baked into `shellArgs`, since VS Code hands the provider
   no direct reference to the `Terminal` it constructs), wired from
   `vscode.window.onDidOpenTerminal` / `onDidCloseTerminal` in `extension.ts`.
   Tests: `test/tmux/terminalProvider.test.ts` (open→close→reopen round-trip
   frees and reuses the slot; ignores non-tmux terminals; closing an
   unknown/foreign terminal is a no-op).

Both fixes: 153/153 tests green (+5 new), `tsc -b` clean, `eslint` clean
(only the pre-existing `allowTemplateLiterals` deprecation warning, unrelated
to this change).
