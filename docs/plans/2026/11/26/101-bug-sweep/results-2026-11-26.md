### Found by the EDH run: double attach after a pty-host revive (fixed, pre-existing)

One row-11 pass on an earlier build of this sweep ended with two `code-*` sessions and **two
clients on one session**. Diagnosis from VSCodium's `terminal.log`: on close and reopen, VS Code
sometimes revives terminals through its pty host (`attachPersistentProcess`). Those terminals carry
no `shellArgs` and never reach the profile provider, so the provider could not recognise them,
waited out its 10 s backstop, opened a second client on each session, and recreated a session the
user had exited in between. This is in v1.4.2 too, and only as likely as VS Code taking that revive
path. Fixed in #87: unlabelled terminals are matched by process id against `list-clients`
(`#{client_pid}`, only this workspace's sessions), in `plan()`, on every revive-wait tick, before
the drain and on open; the drain re-lists the remote and drops sessions that ended or gained a
client. **Proof level:** unit tests for every ordering, plus a rig test that `#{client_pid}` is the
pid of the real client process on 2.6 and 3.4. VS Code did not take the pty-host path in any of the
12 final-build runs of rows 03/08/11, so the end-to-end replay of that exact path is not recorded.
