**Row 35 on tmux 3.8: DOCUMENTED (upstream tmux bug).** Ctrl-B and Esc each arrive exactly once, but every
Esc is held ~545 ms (baseline 44 ms). Verified with `tmux -vv`: VS Code's pty reports a 0 pixel size, so tmux
3.8 sends `CSI 18t` + `CSI 14t` and sets its window-size-query flag; xterm.js answers `18t` but never `14t`, and
3.8 clears the flag only on a `14t` reply, while that flag forces a 500 ms minimum escape delay. This is tmux
issue #5777, fixed on tmux master by `2b12402` ("Apply timeout to window size queries as well", not in a
release yet). tmux 2.6–3.7 are unaffected (no pixel query, or no 500 ms rule). No safe fix exists in our argv:
there is no option for it; a fake reply would leak into the pane; changing the terminal type is server-wide
and disables other features. Documented in README "Known limitations".

## Second pass (rows 3–5, 11, 12, 14–17, 19–21, 36, base pass): product bugs found

None. Findings that were test-side, recorded so nobody re-chases them:

- **tmux escapes `$` in `#{pane_current_path}`** (`/tmp/a $HOME b` prints as `/tmp/a \$HOME b`, verified on
  3.4). The real cwd (`/proc/<pane_pid>/cwd`, `pwd`) is exact; row 16 reads `/proc`.
- **tmux 2.6, typing into the first resize of an adopted terminal.** An adopted/handed-off terminal is
  attached at VS Code's default 80x30 and resized when it is first shown; keys typed within that redraw
  were scrambled by readline on 2.6 (not on 3.4/3.8). A person cannot type that fast after the panel
  appears; the rows wait for a quiet prompt after showing the terminal, as every other typed line already
  did, and then assert the command's *output* line (not the echoed keystrokes).
- **Notification source line.** The lifetime warning (row 36) and other notifications show VS Code's own
  "Source: Open Remote - SSH (tmux)" footer — the extension's display name, not text of ours. Row 10's
  invisibility criterion was judged against the message text; flagged here in case the owner wants the
  display name reconsidered.

## Bugs the first pass found (all fixed in #68, each with unit + rig/EDH coverage)

## Field replay (step 6)

**What ran.** The **published v1.4.1** vsix (`gh release download v1.4.1`, `sha256sum -c` OK), in the EDH client
image (VSCodium 1.143.17232 + Xvfb + xdotool, `--log trace`), connected to **the owner's dev box** (Linux,
tmux 3.4, the VSCodium server for this commit already installed and shared with the owner's own windows)

user settings `reapOnConnect: false`, `handOff: "never"`, `orphanMaxAgeDays: 0`; a throwaway folder

pre-run snapshot; private key mounted read-only; host key pinned from the client machine's known_hosts. The
driver was a scratch adaptation of `test/rig/edh/` (`lib.sh` client helpers, remote helpers over ssh); nothing
in the repo changed except this file.

Three tabs, not two, were live from the second connect on: VS Code's pty host on the shared server revived the
terminal layout of the previous (killed) attempt for this workspace, and the extension backed it with a tmux
session (`new slot 0`). Tabs == sessions held at every step; the driver continued with N = 3.

**Two earlier attempts** (kept for the record, not product failures of the replay):
1. *Environment:* the client container's traffic left via the host's WireGuard VPN (MTU 1420) from a 1500-MTU
   docker bridge; the ~10 KB install-script exec never arrived, and after 60 s the resolver logged
   `Error resolving authority` / `Unable to exec` (1 Error line). Fixed with a 1380-MTU docker network; not a
   product issue (plain `ssh` from the same container hung the same way at key exchange).
2. *Finding (product, low severity — reported, not fixed):* **first terminal after a first connect can be a
   plain shell on a real-latency link.** The Workspace-scope default-profile write (`.vscode/settings.json` on
   the remote) took ~6 s; `DEFAULT_PROFILE_WRITE_DEADLINE_MS` (5000, `src/extension.ts:1025`) expired, the layer
   logged `Could not set default tmux terminal profile: … did not finish within 5000ms` and then `wired`; the
   file landed ~1 s later. New Terminal pressed right after `wired` opened a plain `bash` (screenshot evidence);
   the next New Terminal was tmux. This is bug B's symptom surviving on a slow link: "wired" no longer implies
   "the default profile is in effect" when the write times out. It only affects a folder's first connect (later
   connects find the setting present). Options for the owner: a longer deadline, or keep New Terminal routed to
   the tmux provider until the write lands. EDH row 01b cannot see it (the rig's write is local and fast).
